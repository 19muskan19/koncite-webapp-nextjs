# DPR Flow & API Reference

## Flow Overview

**Bulk flow only** – All DPR creation/update uses `POST /api/dpr-bulk-add`. No step-by-step individual API calls.

## Wizard Steps

1. **Project** – Select project
2. **Subproject** – Select subproject (optional)
3. **Activities** – Select activities; user can add new via "Create New"
4. **Materials** – Select materials; user can add new via "Create New"
5. **Labour** – Select labour; user can add new via "Create New"
6. **Assets (Machines)** – Select assets; user can add new via "Create New"
7. **Safety** – Add safety entries (optional)
8. **Hindrance** – Add hindrance entries (optional)
9. **Hindrance Next** → `dpr-bulk-add` → PDF generated by backend → opens in new tab

## Bulk DPR Flow (POST /api/dpr-bulk-add)

The bulk API processes everything in one request:

1. Process DPR (create/update)
2. Process Activities (with activities_images)
3. Process Materials
4. Process Labour
5. Process Assets
6. Update DPR reference IDs
7. Process Safety (with safety_images)
8. Process Hinderance (with hinderance_images)
9. Generate PDF (generatebluckPDF)
10. DB commit
11. Return results with `dpr_pdf` (including `pdf_url`)

## After Hindrance Next

- Frontend calls `dprAPI.bulkAdd(formData)`
- Response includes `results.dpr_pdf.pdf_url` – used for View/Download
- DPR id extracted from `res.dpr`, `res.results.dpr`, etc.
- `fetchDprList` refreshes list after 800ms
- PDF opens in new tab via returned `pdf_url` (or fallback `generate-pdf`)

## APIs Used

| API | Method | Purpose |
|-----|--------|---------|
| `/api/dpr-list` | GET | List DPRs |
| `/api/dpr-bulk-add` | POST | Create/update DPR and all related data |
| `/api/dpr-edit/{id}` | GET | Get DPR for editing |
| `/api/dpr-details/{id}` | GET | Full DPR with activities, materials, etc. |
| `/api/dpr-delete/{id}` | DELETE | Delete DPR |
| `/api/dpr-check` | GET | Incomplete DPRs |
| `/api/generate-pdf` | POST | Generate PDF (fallback when bulk doesn't return pdf_url) |
| `/api/hinderance-list` | POST | List hindrances (payload: dprId) |
| `/api/hinderance-add` | POST | Standalone – not used when bulk flow |
| `/api/safety-list` | POST | List safety entries |

## Create vs Edit

- **Create new**: User clicks "Create New DPR" or changes project/subproject after Edit → `dpr[id]` is NOT sent → backend creates new DPR and generates new PDF.
- **Edit existing**: User clicks Edit on a DPR → `dpr[id]` IS sent → backend updates that DPR.
- Frontend clears `editingDprId` when user selects/changes project or subproject so a new selection always creates, never updates.

## FormData Structure (dpr-bulk-add)

- `dpr` (PHP array): `projects_id`, `sub_projects_id`, `name`, `staps: 7`
- When **editing**: add `dpr[id]` with the DPR id
- When **creating new**: add `dpr[force_new]=1` – backend must always create new record, never find-and-update by project+subproject+date

**Backend (Laravel)**: When `dpr[force_new]=1` is present and `dpr[id]` is absent, always run `Dpr::create(...)` and never use a find-or-update by `projects_id`+`sub_projects_id`+`name` (date). This fixes the bug where creating a new DPR for the same project+date was updating the existing one.
- `activities` (JSON)
- `activities_images[i][j]`: files
- `materials` (JSON)
- `labour` (JSON)
- `assets` (JSON)
- `safety[i][name]`, `safety[i][details]`, `safety[i][remarks]` (PHP array format)
- `safety_images[i][j]`: files
- `hinderance[i][name]`, etc. (PHP array format)
- `hinderance_images[i][j]`: files

## View / Download

- **View** – Opens PDF in new tab using `completedPdfUrl` (from bulk response) or `generate-pdf`
- **Download** – Same; uses `completedPdfUrl` or calls `generate-pdf`
